# Family Tasks

Home-Assistant-Integration zur Verwaltung wiederkehrender Familien-Aufgaben (Putzplan-Rotation, Punkte) über `config_flow`, `DataUpdateCoordinator` und eine Storage Collection – keine YAML-Integration.

## Struktur

```
custom_components/family_tasks/
  __init__.py                          Setup, Services (complete_task/skip_task), Frontend-Registrierung
  config_flow.py                        Einmaliges Setup + Options-Flow (Karenzzeit, Default-Rotationsstrategie,
                                          Standard-Batteriewarnschwelle)
  storage.py                             StorageCollections für Tasks/Members/Battery-Overrides + Websocket-CRUD-API
                                          (inkl. Rollen-Guard für Mitglieder-CRUD und den
                                          nicht-admin-Befehl family_tasks/task/create_own)
  coordinator.py                          Berechnet Status/Fälligkeit/Rotation/Punkte aus Storage + Completion-Log
  battery.py                              Batterie-Erkennung (Entity Registry) + Aggregation für die
                                          Batteriewarnung-Aufgabe (Rekurrenztyp "battery")
  sensor.py / button.py                    Dynamische Entities je Task/Mitglied
  www/family-tasks-card.js                Lovelace-Karte (CRUD über die Websocket-API, keine Build-Tools nötig)
  www/family-tasks-leaderboard-card.js    Lovelace-Bestenliste (Wochen-/Monatsansicht)
tests/                                    pytest-homeassistant-custom-component Testsuite
```

## Installation in Home Assistant

1. `custom_components/family_tasks/` in das `custom_components`-Verzeichnis deiner HA-Konfiguration kopieren (bzw. den ganzen Ordner per Samba/SSH dorthin syncen).
2. Home Assistant neu starten.
3. Einstellungen → Geräte & Dienste → Integration hinzufügen → „Family Tasks" suchen, Anzeigename bestätigen.
4. Dashboard bearbeiten → Karte hinzufügen → „Family Tasks" auswählen (oder manuell `type: custom:family-tasks-card`). Die Karte lädt sich automatisch, es ist keine manuelle Lovelace-Resource nötig.
5. In der Karte zunächst Familienmitglieder anlegen (optional mit `person.*`-Verknüpfung und Rolle „Kind", wenn die Erledigung von einem Elternteil bestätigt werden soll), danach Aufgaben mit Wiederholung, Fälligkeit und Rotation. Wiederholung kann „Täglich", „Wöchentlich", „Alle N Tage", „Einmalig" (ein einzelner, nie wiederkehrender Termin) oder „Sensor-Ereignis" sein.
6. „Erledigt" in der Karte oder die Services `family_tasks.complete_task` / `family_tasks.skip_task` in Automatisierungen nutzen. Ist die zugewiesene Person ein „Kind"-Mitglied, wird die Aufgabe erst als „Wartet auf Bestätigung" markiert und eine Bestätigungsaufgabe für die Eltern angelegt (außer die Aufgabe hat „Bestätigung durch Eltern erforderlich" explizit deaktiviert); erst wenn ein Elternteil diese abschließt, gelten Punkte/Rotation als vergeben (Ablehnen über „Überspringen" auf der Bestätigungsaufgabe setzt die Aufgabe zurück).
7. In der Kopfzeile „Aufgaben" lassen sich per Button nicht-fällige Aufgaben ausblenden sowie auf „Nur eigene Aufgaben" filtern (bezogen auf das über die verknüpfte `person`-Entität ermittelte, zum eingeloggten HA-Benutzer gehörende Mitglied). Bei Rotation „Fest zugewiesen" mit mehreren ausgewählten Mitgliedern zeigt der Filter die Aufgabe allen diesen Mitgliedern an, nicht nur demjenigen an `rotation.current_index` - eine fest zugewiesene Aufgabe mit mehreren Personen rotiert ohnehin nie, sie wird also geteilt statt „gerade jemandem zu gehören". Bei jeder anderen Rotationsoption bleibt es dabei, dass nur die aktuell zuständige Person die Aufgabe sieht. In der Kopfzeile „Familienmitglieder" lässt sich die komplette Mitglieder-Sektion (Überschrift, Liste, „+ Mitglied hinzufügen") ein-/ausblenden, ebenso die Sektion „Batterien" (siehe Punkt 12). Über den kleinen Button oben rechts in der Karte lassen sich die Umschalt-Buttons komplett verbergen, um die Karte im Alltag kompakt zu halten. Alle Einstellungen werden pro Gerät/Browser gespeichert (localStorage) und überstehen ein Neuladen des Dashboards.
8. Bearbeiten/Löschen von Aufgaben ist in der Karte nur für Home-Assistant-Administratorkonten sichtbar (Home Assistant lehnt diese Aktionen für Nicht-Admins serverseitig ohnehin ab). Für Familienmitglieder gilt zusätzlich: ein Benutzer, der (über `person_entity_id` → die verknüpfte Person → deren `user_id`) einem Mitglied mit Rolle „Kind" zugeordnet ist, bekommt nie Mitglieder-Verwaltung angezeigt und wird serverseitig abgelehnt (`MemberStorageCollectionWebsocket`) - unabhängig vom Admin-Status des HA-Kontos. Aufgaben erledigen/überspringen funktioniert für alle Konten weiterhin, da das über die Services `complete_task`/`skip_task` läuft.
9. Ein Benutzer, der einem „Kind"-Mitglied zugeordnet ist, sieht zusätzlich „+ Eigene Aufgabe hinzufügen" - ganz ohne Admin-Rechte, über den eigenen Websocket-Befehl `family_tasks/task/create_own`. Dabei werden Punkte immer auf 0 und die Zuweisung immer auf das eigene Mitglied erzwungen; wählbar ist lediglich, ob die Aufgabe eine Eltern-Bestätigung benötigt.
10. Rotationsstrategie „Wenigste Punkte" weist eine Aufgabe jeweils demjenigen Mitglied im Rotationspool zu, das aktuell die wenigsten Punkte hat (bei Gleichstand das erste in der Liste); die Option „Nur Punkte von Kindern berücksichtigen" schränkt diesen Vergleich auf Mitglieder mit Rolle „Kind" ein.
11. Die Karte „Family Tasks Leaderboard" (`type: custom:family-tasks-leaderboard-card`) zeigt eine nach Punkten sortierte Bestenliste mit umschaltbaren Ansichten „Woche" und „Monat". Hinter dem Namen steht keine Rollenangabe mehr.
12. Batterie-Entities, die Home Assistant kennt (`sensor`/`binary_sensor` mit `device_class: battery`), werden automatisch überwacht - dafür ist keine eigene Aufgabe nötig. Sobald eine davon ihren Warn-Schwellenwert erreicht oder unterschreitet (bzw. ein Binärsensor „niedrig" meldet), legt die Integration selbstständig eine einmalige Aufgabe an, die genau diese Batterie nennt, und weist sie allen Familienmitgliedern zu, die über eine verknüpfte Person mit einem Home-Assistant-Administratorkonto verbunden sind; sie taucht wie jede andere Aufgabe in der Liste auf und wird über „Erledigt"/„Überspringen" abgeschlossen. Pro Batterie bleibt es bei höchstens einer offenen Alarm-Aufgabe gleichzeitig - erst wenn diese erledigt/übersprungen wurde, kann beim nächsten Unterschreiten wieder eine neue entstehen. Der admin-only Kartenabschnitt „Batterien" (unterhalb der Aufgabenliste, über die Kopfzeile ein-/ausblendbar) dient ausschließlich der Konfiguration: er listet jede erkannte Batterie und erlaubt es, sie einzeln von der Überwachung auszuschließen oder ihr eine eigene Warnschwelle zu geben, über die Websocket-API `family_tasks/battery_override/*`. Der Standard-Schwellenwert (20 %, sofern nicht geändert) wird über die Integrations-Optionen (Einstellungen → Geräte & Dienste → Family Tasks → Konfigurieren) festgelegt. Die ältere Wiederholung „Batteriewarnung" (eine von Hand angelegte und zugewiesene Sammel-Aufgabe) funktioniert für bereits bestehende Aufgaben unverändert weiter, steht beim Neuanlegen aber nicht mehr zur Auswahl.

## Tests

Die Suite nutzt [pytest-homeassistant-custom-component](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component), das täglich gegen die aktuelle HA-Version gebaut wird – dafür wird **Python 3.13** benötigt (aktuelle HA-Mindestanforderung).

```bash
python3.13 -m venv .venv
source .venv/bin/activate
pip install -r requirements_test.txt
pytest
```

Abgedeckt sind: Config-Flow (Singleton-Setup), Storage-Collection-Validierung/-Merge-Verhalten, Coordinator-Logik (Status-Berechnung, Rotation, Punktevergabe, Idempotenz von `complete_task`, `skip_task`, Overdue-Erkennung), Kind-Bestätigungs-Workflow, die Rollen-Guards für Mitglieder-CRUD/`create_own_task` (`tests/test_permissions.py`), die Rekurrenz „einmalig", Rotation „Wenigste Punkte" (inkl. „Nur Kinderpunkte") und das `requires_confirmation`-Override (`tests/test_new_features.py`), die Batteriewarnung-Aufgabe (Rekurrenztyp „battery", weiterhin unterstützt): Erkennung über die Entity Registry, Aggregation/Schwellenwert-Logik inkl. Ausschluss und Pro-Entity-Override, sowie das idle/pending-Verhalten der Coordinator-Aufgabe (`tests/test_battery.py`, plus Storage-Validierung in `tests/test_storage.py`), sowie (neu, v0.6) die automatischen Batterie-Alarm-Aufgaben: korrekt benannte/zugewiesene Aufgabe je Batterie, keine Duplikate bei anhaltend niedrigem Stand, neue Aufgabe nach Erledigen der vorherigen, Zuweisung ausschließlich an admin-verknüpfte Mitglieder, Ausschluss über `battery_override` (`tests/test_battery_alerts.py`).

**Hinweis zur Verifikation während der Entwicklung:** Die pytest-Suite selbst konnte in der Entwicklungsumgebung nicht ausgeführt werden, da dort nur Python 3.10 mit einem auf `homeassistant==2023.7.3` eingefrorenen `pytest-homeassistant-custom-component`-Mirror verfügbar ist, der Code aber gegen eine deutlich aktuellere HA-Version geschrieben ist (`StaticPathConfig`, `EventStateChangedData`, `ConfigEntry.runtime_data`/`config_entry`-Kwarg für `DataUpdateCoordinator` u. a. existieren dort schlicht nicht - `ConfigEntry` hat dort außerdem `__slots__` ohne `runtime_data`, sodass sich das auch nicht sinnvoll nachrüsten lässt). Stattdessen wurde die neue Logik direkt gegen den echten Code verifiziert, unter Umgehung nur des Pakets `__init__.py` (das die inkompatiblen Frontend-/Coordinator-Imports enthält): `const.py`/`storage.py`/`battery.py`/`coordinator.py` wurden isoliert importiert (nach `import pytest_homeassistant_custom_component.plugins`, plus einem minimalen Stub für `homeassistant.core.EventStateChangedData`, das in dieser HA-Version noch fehlt und nur als Typ-Hint verwendet wird), und darüber mit einer echten `hass`-Instanz (`async_test_home_assistant`) durchgespielt: `battery.async_discover_battery_entity_ids`/`async_compute_low_batteries` gegen eine echte Entity Registry + echte States (numerischer Sensor unter/über Schwelle, binärer Low-Battery-Sensor, deaktivierte Registry-Entities, Ausschluss- und Pro-Entity-Schwellenwert-Override inkl. Zurücksetzen), `storage.BatteryOverrideStorageCollection` (Defaults, Schwellenwert-Range-Validierung, Merge-Verhalten bei Update) sowie `storage.TaskStorageCollection` mit Rekurrenztyp „battery" (kein `anchor_date`/`trigger` nötig) und `coordinator._current_period_date`/`_due_at` für „battery" (behandelt wie „daily") - alle bestanden. Der Coordinator selbst (`FamilyTasksCoordinator`, der `DataUpdateCoordinator` mit `config_entry=`-Kwarg instanziiert) sowie der volle `async_setup_entry`-Durchlauf (`init_integration`-Fixture) ließen sich aus obigem Grund in dieser alten HA-Version nicht instanziieren/ausführen - das mit `pytest.mark` versehene `tests/test_battery.py` wurde daher **nicht** durch einen echten `pytest`-Lauf bestätigt, ebenso wenig wie die bereits bestehenden Testdateien. **Für v0.6** wurde derselbe Ansatz erweitert: `FamilyTasksCoordinator._async_raise_battery_alerts`/`_async_admin_member_ids` wurden als ungebundene Methoden gegen ein händisch gebautes, „duck-typed" Coordinator-Objekt (echte `hass`-, `TaskStorageCollection`-, `MemberStorageCollection`-, `CompletionLogStore`-Instanzen, ohne die eigentliche `FamilyTasksCoordinator.__init__`) durchgespielt - das umgeht genau das `config_entry=`-Problem, ohne die Methodenlogik selbst zu verändern. Geprüft: leere Alarmliste ohne niedrige Batterie, korrekt benannte/typisierte Aufgabe je niedriger Batterie (numerisch mit %, binär ohne), keine Zuweisung ohne Admin-verknüpftes Mitglied, korrekte Zuweisung sobald eins existiert, keine Duplikate bei wiederholtem Refresh, neue Aufgabe nach Erledigen der alten, kein Alarm für ausgeschlossene Batterien - alle bestanden (siehe `tests/test_battery_alerts.py` für die entsprechenden, noch nicht per echtem `pytest`-Lauf bestätigten Fälle). Die JS-Änderungen (`family-tasks-card.js`/`family-tasks-leaderboard-card.js`) wurden per `node --check` auf Syntaxfehler und der neue „Nur eigene Aufgaben"-Filter zusätzlich isoliert in Node gegen mehrere Rotations-Kombinationen (fest/geteilt, fest/einzeln, reihum, wenigste Punkte, ohne verknüpftes Mitglied) durchgespielt. Bitte vor dem nächsten Feature-Ausbau einmal lokal (mit passender HA-Version, Python 3.13) `pytest` laufen lassen.
